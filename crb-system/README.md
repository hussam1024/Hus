# نظام الإدارة المتكامل: منتدى الإغاثة والبناء (CRB)

**Coalition of Relief and Building: Integrated Management System**

هذا نظام ويب داخلي خاص بطاقم المنتدى. يحلّ محلّ الإيميلات المتفرقة والعمل العشوائي، وهو مبني بالكامل على **دليل العمليات الإدارية (الإصدار الأول، نوفمبر 2026)**: 15 عملية للمشاريع، و6 عمليات للطلبات، والعمليات الاستثنائية (أ) و(ب). التصميم يتبع هوية المنتدى: الأخضر `#01A453` والبرتقالي `#EF7023` والشعار الرسمي.

---

## 1. التشغيل السريع

يحتاج النظام إلى **Node.js 22.13 أو أحدث**، ولا يحتاج قاعدة بيانات خارجية. البيانات تُحفظ في ملف SQLite واحد داخل `data/`.

```bash
cd crb-system
npm install
npm start
```

افتح بعدها `http://localhost:3000`.

عند **أول تشغيل** يطبع النظام اسم مستخدم المضيف الرئيسي (`admin`) وكلمة مرور مؤقتة، ويحفظها أيضًا في `data/FIRST_LOGIN.txt`. ادخل بها، وسيطلب منك النظام تغييرها فورًا. احذف الملف بعد ذلك.

إذا أردت تحديد كلمة المرور الأولى بنفسك:

```bash
CRB_ADMIN_PASSWORD='YourStrongPass2026' npm start
```

### تجربة النظام ببيانات تجريبية

```bash
npm run demo
npm start
```

يُنشئ هذا الأمر 13 موظفًا تجريبيًا موزعين على الإدارات، و6 مشاريع في مراحل مختلفة، وطلبات ونقاشات ومهام. كلمة مرور جميع الحسابات التجريبية هي `Demo@2026`، ومنها: `fin.head` و`log.officer` و`media.officer` و`prj.head` و`sec.head` و`auditor`.
احذف الحسابات التجريبية (أو ابدأ بمجلد `data/` فارغ) قبل الاستخدام الفعلي.

### الاختبار الآلي

```bash
npm test
```

يشغّل 32 فحصًا على الصلاحيات وعزل الإدارات وسير العمل والقفل بعد المحاولات الخاطئة وغيرها.

## 2. النشر على خادم (للعمل من أي مكان)

**باستخدام Docker:**

```bash
docker build -t crb-system .
docker run -d --name crb -p 3000:3000 -v crb-data:/data -e CRB_SECURE_COOKIE=1 -e CRB_TRUST_PROXY=1 --restart unless-stopped crb-system
```

ضع أمامه خادمًا يوفر **HTTPS** (مثل Nginx + Let's Encrypt، أو Caddy، أو Cloudflare Tunnel). هذا شرط أساسي لأن كلمات المرور تمر عبر الشبكة.

| المتغير | الوظيفة |
|---|---|
| `PORT` | منفذ التشغيل (الافتراضي 3000) |
| `CRB_DATA_DIR` | مجلد قاعدة البيانات والمرفقات |
| `CRB_ADMIN_USER` / `CRB_ADMIN_PASSWORD` | حساب المضيف الرئيسي عند أول تشغيل فقط |
| `CRB_SECURE_COOKIE=1` | يُفعَّل عند العمل خلف HTTPS |
| `CRB_TRUST_PROXY=1` | يُفعَّل عند العمل خلف Nginx/Proxy، ليُسجَّل عنوان IP الحقيقي |
| `CRB_SESSION_HOURS` | مدة الجلسة (الافتراضي 10 ساعات، وتتجدد مع النشاط) |
| `CRB_MAX_UPLOAD_MB` | الحد الأقصى لحجم الملف المرفوع (الافتراضي 25) |

**النسخ الاحتياطي:** من «الإعدادات والنسخ الاحتياطي» اضغط «تنزيل نسخة احتياطية». أو انسخ مجلد البيانات كاملًا (`crb.sqlite` و`uploads/`).

## 3. أنت المضيف الرئيسي: كيف تدير النظام؟

### توزيع الحسابات وكلمات المرور
1. افتح **«المستخدمون وكلمات المرور»** واضغط **«إنشاء حساب موظف»**.
2. اكتب الاسم واسم المستخدم، واختر **الإدارة** و**الدور**.
3. يولّد النظام **كلمة مرور مؤقتة قوية** تظهر مرة واحدة فقط. انسخها وسلّمها للموظف شخصيًا.
4. عند أول دخول **يُجبر الموظف على تغييرها**. بعد ذلك لا يعرفها أحد غيره، لأن كلمات المرور مشفّرة بـ bcrypt.
5. إذا نسي الموظف كلمة المرور، اضغط 🔑 «إعادة تعيين» لتوليد كلمة مؤقتة جديدة. هذا يُخرجه أيضًا من كل أجهزته.
6. عند مغادرة موظف، **أوقف** حسابه ولا تحذفه، حتى يبقى سجله التاريخي محفوظًا.

### الصلاحيات: من يدخل أين، ومن يفعل ماذا

```
الصلاحية الفعلية = صلاحيات الإدارة (المجال) + صلاحيات الدور (المستوى) + منح فردي − منع فردي
```

| الطبقة | المعنى | مثال |
|---|---|---|
| **الإدارة** | تحدد **أي التبويبات يدخلها** الموظف | موظف المالية يدخل تبويب المالية، ولا يرى الإعلام ولا السكرتارية |
| **الدور** | يحدد **مستوى ما يفعله** | موظف ينفّذ. مدير الإدارة يُسند المهام ويُرجع الأخطاء. المدير العام يعتمد. المدقق يطّلع فقط |
| **الاستثناء الفردي** | منح صلاحية لشخص بعينه أو منعه منها | السماح لمحاسب واحد برؤية الإعلام، أو منع موظف من النقاش |

تعدّل كل ذلك من **«الأدوار ومصفوفة الصلاحيات»**:
- **صلاحيات الأدوار**: مصفوفة خانات، وكل تغيير يُحفظ فورًا.
- **صلاحيات الإدارات**: مصفوفة بنفس الطريقة.
- **خريطة الوصول**: جدول يُريك بنظرة واحدة **من يدخل ماذا** لكل موظف.

### الأدوار الجاهزة
| الدور | الوصف |
|---|---|
| المضيف الرئيسي | كل الصلاحيات دائمًا، ولا يمكن تقييده |
| المدير العام | يطّلع على كل شيء (CC)، ويعتمد المراحل، ويوقّع العقود، وينشر التعميمات، ويعتمد الإجازات |
| مدير إدارة | ينفّذ مراحل إدارته، ويُسند المهام لفريقه، ويُرجع الأخطاء، ويدير الاجتماعات |
| موظف | ينفّذ المراحل والمهام الخاصة بإدارته |
| مدقق / مراقب | اطلاع فقط على كل الوحدات دون أي تعديل (للمراجعة الداخلية أو المانح) |

### هل يستطيع موظف دخول صفحة إدارة أخرى بكتابة الرابط مباشرة؟
**لا.** كل طلب بيانات يمر بالتحقق من الصلاحية **في الخادم** نفسه، ولا يكفي إخفاء الزر في الواجهة. المحاولة تُرفض وتُسجَّل باسم صاحبها في **سجل التدقيق**.

## 4. الوحدات (التبويبات)

| الوحدة | المحتوى |
|---|---|
| **لوحة التحكم** | لوحة شخصية لكل موظف: «بانتظار إجرائك الآن»، ومهامك، والتعميمات، ومؤشرات الأداء، والمشاريع المتوقفة، ومواعيد التنفيذ |
| **المشاريع** | الـ15 مرحلة كما في الدليل: الجهة المنفذة والمستلمة والوسيلة والإجراء والمخرج، مع **تأكيدات مكتوبة إلزامية**، و**شروط بيانات** قبل كل انتقال، و**اعتماد المدير العام** في المراحل 4 و6 و11. ولها عرض قائمة وعرض لوحة مراحل |
| **الطلبات** | المراحل الـ6، مع **مهل متدرجة**: مهلة القطاع لا تتجاوز مهلة المانح، ومهلة الموظف أقصر من مهلة القطاع احتياطًا. وتظهر تنبيهات للطلبات المتأخرة |
| **اللوجستيات** | سجل الموردين وتقييمهم، وعروض الأسعار مع **تمييز الأقل سعرًا تلقائيًا**. اختيار عرض غير الأقل يتطلب مبررًا مكتوبًا. وفيها العقود (العملية ب) ومطالبات الموردين |
| **المالية** | المخصص الإداري مع **حساب المبلغ المعتمد تلقائيًا**، وصرف المطالبات المعتمدة فقط بالشيك والبنك، ودفتر الحركات، ونسبة الصرف لكل مشروع |
| **الإعلام** | خطة التغطيات، والإعلامي المكلف، والرابط المعتمد، والحالة (تم الرفع، ثم تم الرفع **والمراجعة**) |
| **السكرتارية** | سجل الوارد والصادر بترقيم تلقائي (و-0001/2026 و ص-0001/2026)، ومتابعة المهل، وقائمة ما ينتظر الرفع للمانح |
| **ساحة النقاش** | قنوات عامة، وقناة لكل إدارة، ونقاش لكل مشروع، ومجموعات عمل، ورسائل خاصة. فيها الإشارة @، والردود، والتفاعلات، والتثبيت، والمرفقات |
| **التعميمات** | تعميمات رسمية مع خيار **«يتطلب تأكيد اطلاع»**، ويرى الناشر من قرأ ومن لم يقرأ |
| **المهام** | لوحة كانبان بالسحب والإفلات: مهامي، وما أسندته، ومهام إدارتي، وكل المنتدى |
| **الاجتماعات** | الدعوات والحضور وجدول الأعمال والمحضر، وتحويل كل قرار إلى **مهمة متابعة** |
| **الإجازات** | الطلب، وتعيين البديل، والاعتماد الإلكتروني، ورصيد الإجازات المستخدمة |
| **التقويم** | تقويم موحد يجمع التنفيذ والمهل والاجتماعات والمهام والتغطيات والإجازات |
| **سجل الأخطاء الشهري** | نموذج الدليل بنفس أعمدته. يُملأ تلقائيًا عند كل «إرجاع لتصحيح خطأ»، ويعرض تحليلًا حسب الإدارة والموظف والمرحلة، ويمكن طباعته وتصديره |
| **التقارير (KPIs)** | متوسط زمن كل مرحلة لكشف عنق الزجاجة، ونسبة الالتزام بمهل المانح، والأخطاء الشهرية، وعبء العمل حسب الإدارة، والمشاريع حسب المانح والقطاع |
| **الأرشيف المركزي** | كل المرفقات مصنفة وقابلة للبحث |
| **دليل العمليات** | الدليل كاملًا داخل النظام، مع دليل استخدام ودليل خاص بالمضيف الرئيسي |
| **سجل التدقيق** | سجل لكل عملية ومحاولة دخول: من، وماذا، ومتى، ومن أي IP |

### كيف طُبّقت القواعد العامة في النظام
1. **المدير العام نسخة CC على كل شيء**: يصله إشعار تلقائي بكل انتقال مرحلة، وكل إرجاع، وكل مشروع أو طلب جديد.
2. **لا انتقال بدون تأكيد مكتوب**: زر «إنجاز المرحلة» لا يعمل قبل التأشير على كل التأكيدات، ويُسجَّل اسم من أكّد وتاريخ التأكيد.
3. **«المراجعة والرفع» معًا**: المرحلتان 8 و9 تشترطان تأكيدين منفصلين: الرفع، ثم المراجعة.
4. **قيد الخطأ على المسؤول**: زر «إرجاع لتصحيح خطأ» يعيد العمل إلى المرحلة التي وقع فيها الخطأ، ويقيّده في السجل الشهري، ويُشعر المسؤول والمدير العام.

## 5. الأمان
- تشفير كلمات المرور بـ bcrypt، وكلمة مرور مؤقتة يجب تغييرها عند أول دخول، وسياسة كلمات مرور (8 أحرف على الأقل، حروف وأرقام).
- قفل الحساب 15 دقيقة بعد 5 محاولات خاطئة، وحد لعدد محاولات الدخول من نفس العنوان.
- جلسات بكوكي `HttpOnly` و`SameSite=Strict`، مع ترويسة إلزامية ضد CSRF.
- سياسة CSP صارمة، وحماية من الإطار (Clickjacking)، وتهريب كل المخرجات ضد XSS.
- الملفات تُحفظ بأسماء عشوائية خارج المجلد العام، ولا تُنزّل إلا لمن يملك صلاحية المشروع أو الطلب أو القناة.
- عند تغيير كلمة المرور أو إيقاف الحساب، يُسجَّل الخروج من كل الأجهزة.

## 6. البنية التقنية
```
crb-system/
├── server/
│   ├── index.js          ← الخادم ورؤوس الأمان
│   ├── db.js             ← المخطط (SQLite مدمج في Node، بلا إعداد)
│   ├── permissions.js    ← فهرس الصلاحيات والأدوار والإدارات الافتراضية
│   ├── workflows.js      ← مراحل الدليل (المشاريع 15، الطلبات 6) بنصها الرسمي
│   ├── core.js           ← الجلسات، والتحقق، والإشعارات، وسجل التدقيق
│   ├── routes/           ← workflow / modules / collab / admin
│   ├── seed.js, demo.js  ← التهيئة الأولى والبيانات التجريبية
├── public/               ← الواجهة (RTL، بلا أدوات بناء)
│   ├── css/app.css       ← نظام التصميم بهوية المنتدى (فاتح/ليلي)
│   └── js/pages/*.js     ← صفحة لكل وحدة
└── test/smoke.js         ← 32 اختبارًا آليًا
```
المكتبات المستخدمة ثلاث فقط: `express` و`bcryptjs` و`multer`. الخط هو IBM Plex Sans Arabic (رخصة OFL)، ومحفوظ داخل المشروع فلا يحتاج اتصالًا بالإنترنت.

## 7. نسخة Claude (بدون خادم)

مجلد `artifact/` يحوي نسخة من النظام تعمل كصفحة منشورة على claude.ai، ببيانات مشتركة بين الطاقم ودون أي استضافة.
- `main.js` منطق الصفحة، و`build.js` يدمجه مع التصميم والمكتبة ومراحل الدليل في ملف واحد `crb.html`.
- لإعادة البناء: `node artifact/build.js`
- الهوية فيها هي حساب Claude لكل موظف (لا كلمات مرور). المضيف الرئيسي هو مالك الصفحة، ويشارك الرابط بصلاحية «محرر»، ويقبل طلبات الانضمام ويحدد الإدارات والأدوار.
- قواعد قاعدة البيانات تمنع غير المالك من تعديل الموظفين والصلاحيات. أما فصل الإدارات عن بعضها فتنظيمي في الواجهة، لأن كل من شوركت معه الصفحة يستطيع تقنيًا قراءة بياناتها. للحماية الصارمة استخدم نسخة الخادم.
